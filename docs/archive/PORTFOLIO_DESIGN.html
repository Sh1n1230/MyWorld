Three Decisions

設計書全体は、この 3 つの判断から演繹されている

判断 1

Unity は「世界」だけを描く。文字はすべて Web が描く。

Unity 内に日本語テキストを持つと、TMP のフォントアトラス（数千グリフ）がビルドサイズとメモリを圧迫し、文章を直すたびに Unity の再ビルドが必要になり、スマホでの可読性調整も難しく、SEO には一切寄与しません。

セリフも作品説明も UI 文字列も、すべて Web 側の DOM でレンダリングします。Unity が持つのは 3D 世界・キャラクター・カメラ・演出・サウンド、そして「今これがインタラクト可能だ」という文字を使わない表現だけ。
→ これ 1 つでフォント問題・多言語・レスポンシブ・アクセシビリティ・SEO が同時に解けます。

判断 2

Unity は一度ロードしたら、絶対にアンマウントしない。

Unity WebGL の初回ロードは 20〜60 秒。作品を 1 つ見るたびにページ遷移して再ロードする体験は成立しません。

作品詳細は DOM オーバーレイ + URL だけを書き換える方式に。同時に、その URL に直接アクセスした場合は静的 HTML ページを返します。同じ URL に 2 つのレンダリング経路を用意することで、SEO・SNS シェア・WebGL 非対応端末のフォールバックが同一 URL 空間で成立します。

判断 3

Unity リポジトリには一切手を触れない。Web は新規リポジトリ。

現行 MyWorld は Git 履歴も LFS も .gitignore も既に健全。手を入れる理由がありません。Web は Sh1n1230.github.io として新規に始めます。移行作業ゼロ = 履歴破壊リスクゼロ。

UX Flow

訪問者が体験する 60 秒

1
言語選択（JA / EN）この画面の裏で Unity WebGL がロードされる。ボタンのクリックは、ブラウザが音声再生を許可するための user gesture も兼ねる — 待ち時間と技術的要件が一致している。
2
入店演出（3〜5 秒）ドアが開く音 → 明転 → カフェの店内。操作方法のヒントを 5 秒だけ表示。
3
探索NPC は常にソワソワしたループアニメーション。照明・BGM の定位・店の動線で自然に視線を誘導する。
4
インタラクション可能を認知距離 4m でタバコが淡く発光 → 2m で小さなアイコン → PC はホバーでアウトライン、Mobile は右下に大きな丸ボタン。
5
火をつけるカメラが 0.6 秒でタバコにフレーミング。着火 SE + パーティクル + 煙。
6
対話 — ポートフォリオ世界への導入カメラが NPC の肩越しへ。DOM の対話ボックスが下からせり上がる。クリック / タップ / Space で送る。

「何をクリックすればいいか分からない」を防ぐ

最も効く対策は UI の工夫ではなく、数の制限です。インタラクト可能オブジェクトを 1 シーンあたり 5〜9 個に厳密に制限する。CAFE は Phase 1 で 1 個だけ。
層発火条件表現実装
L1 環境的誘導常時照明・色・動線・アニメ・音の定位。UI ではないUnity（レベルデザイン）
L2 近接ヒント距離 < 4mリムライトが距離に応じてフェードイン。2m でアイコンUnity
L3 照準ヒントホバー / 最優先対象アウトライン + カーソル変化 + ラベルUnity + Web

PC とスマホ

PC
  • 移動 = WASD
  • カメラ = 右ドラッグ
  • インタラクト = 左クリック / E

ポインタロックは使いません。カーソルが見えていることが「クリックできる対象がある」という認知の前提になるため。没入感より確実性を優先します。

Mobile
  • 移動 = 左半分の仮想スティック
  • カメラ = 右半分のスワイプ
  • インタラクト = タップ または近接時の丸ボタン

丸ボタンは必須です。モバイルに hover はなく、小さな 3D 対象を正確にタップさせるのは失敗率が高いため、「近づけば必ず押せる」保険を用意します。

通信

方向方式
Web → UnityunityInstance.SendMessage("WebBridge", "Receive", json)
Unity → Web.jslib → window.dispatchEvent(new CustomEvent("unity:message"))

メッセージはすべて 1 つの封筒型に統一します。種類ごとに関数を生やすと SendMessage の受け口が増えて破綻するためです。

{ v: 1, id: string, type: "CIGARETTE_LIT", payload: {...}, ts: number }

BRIDGE_READY が来るまで Web は送信をキューに積み、未知の type は双方向とも warn して無視します（前方互換 — 絶対に例外を投げない）。

デプロイ — GitHub Pages の制約への対応

GitHub Pages はカスタム HTTP ヘッダを設定できません。これが 2 つの帰結を生みます。

  • Content-Encoding: gzip を返せない → Unity の Decompression Fallback を ON にする必要がある
  • Content-Type: application/wasm を返せない → WASM ストリーミングコンパイルが効かず起動がやや遅い（動作はする）

また公開サイト 1 GB / 帯域 100 GB 月（ソフト）の上限があるため、ビルド成果物をリポジトリ履歴に溜めない方式にします。

main       : ソースのみ。バイナリは一切入らない（public/unity/ は gitignore）
gh-pages   : 常に 1 コミットだけ。デプロイのたびに履歴ごと force push で上書き

GitHub Actions で Unity をビルドしない理由: ライセンス secret、6 GB 超の checkout、そして LFS 帯域（1 回のフルチェックアウトで約 0.9 GiB / 無料枠 10 GiB 月）が必要になり、月 10 回で枠を使い切ります。ポートフォリオ 1 個にこのコストは見合いません。Unity は Editor でビルドするのだから、そのままローカルから流すのが自然です。

Phase 0 を独立させる理由

このプロジェクトの最大の未知数は「Unity WebGL が GitHub Pages 上で、実機のスマホで、許容できる速度で動くか」です。ここが破綻すると、その後の設計がすべて無意味になります。だからブリッジもオーバーレイも作る前に、まず現状の CAFE をそのまま公開して iPhone で開いてみます。
