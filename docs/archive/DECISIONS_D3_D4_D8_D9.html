Decision D3

どこにホスティングするか

D3Cloudflare Pages を第一候補にする

なぜホスティング選びが Unity WebGL では特別なのか

普通の Web サイトなら、ホスティングはどこでも大差ありません。HTML が数十 KB、画像が数 MB という世界だからです。ところが Unity WebGL は初回に数十 MB を一気にダウンロードさせるという、Web としては極めて異例の性質を持ちます。だからホスティングの「転送まわりの細かい仕様」が、そのまま体験の良し悪しになります。

具体的に効いてくるのは、次の 3 点だけです。

1
カスタム HTTP ヘッダを設定できるかファイルを Brotli 圧縮して置いたとき、「これは Brotli で圧縮済みです」とブラウザに伝える必要があります。この伝達手段が Content-Encoding: br というヘッダです。これを設定できないと、ブラウザは圧縮を解けず、Unity 側で JavaScript を使って自力で解凍することになります（＝遅い）。
2
1 ファイルあたりのサイズ上限Unity は 3D モデルやテクスチャを .data という1 個の巨大なファイルにまとめます。これは分割できません。ホスティング側に「1 ファイル ◯ MB まで」という制限があると、ここに引っかかります。
3
帯域（月あたりの転送量）1 人が訪問するたびに数十 MB 転送されます。仮に 30 MB のサイトに月 1,000 人が来ると 30 GB。ポートフォリオならまず問題になりませんが、一応見ておく項目です。

ただし Cloudflare Pages には落とし穴がある

Cloudflare Pages は 1 ファイル 25 MiB までしか置けません。Unity の .data ファイルは分割できない単一ファイルなので、これを超えるとデプロイが失敗します。

つまり Phase 0 の実測結果が、そのままホスティングの選択を決めます。この意味でも「まず現状のまま 1 回ビルドしてサイズを測る」ことが先決です。

GitHub Pages を選ぶ余地はあるか

あります。GitHub Pages の利点は「新しいアカウントもサービスも増やさなくていい」という一点で、これは初学者にとって決して小さくありません。管理するものが増えないのは実際に価値があります。

ただし今回の場合、どのサービスも「GitHub リポジトリを連携して push すると自動デプロイ」という同じ使い方ができるので、最初の 10 分だけ手間が増える代わりに、恒久的に起動が速くなるという交換になります。ポートフォリオは訪問者の第一印象がすべてなので、この交換は割に合うと考えます。

なお、この選択はいつでもやり直せます。今回の設計はホスティングに依存する部分が一切ありません（静的ファイルを置くだけ）。「まず GitHub Pages で公開して、遅いと感じたら移す」でも損はしません。移行作業は実質、別のサービスに同じリポジトリを連携するだけです。

Decision D4

Unity の圧縮設定をどうするか

D4Brotli + Decompression Fallback OFF

これは D3 に完全に連動する決定です。まず「Decompression Fallback」が何なのかを説明します。

Decompression Fallback とは何か

Unity はビルド時にファイルを圧縮します。その圧縮ファイルをブラウザが受け取ったとき、誰が解凍するのかには 2 通りあります。

Fallback OFF（ヘッダを設定できる場合）
サーバー
  ↓ 「これは Brotli です」と
  ↓  ヘッダで伝える
ブラウザ
  ↓ 自分で解凍する
  ↓ （C++ で実装された
  ↓   ネイティブ機能・高速）
Unity が起動
Fallback ON（ヘッダを設定できない場合）
サーバー
  ↓ 何も伝えられない
  ↓ （ただのバイナリ扱い）
ブラウザ
  ↓ 解凍できないのでそのまま渡す
Unity のローダー JS
  ↓ JavaScript で自力解凍
  ↓ （解凍プログラムを
  ↓   同梱する分だけ肥大）
Unity が起動

Fallback は「サーバーが協力してくれないときの保険」です。保険が要らない環境なら切るべきで、切れば速くなり、ローダーも小さくなります。

Gzip と Brotli の使い分け

GzipBrotli
圧縮率普通高い（Gzip より 15〜25% 小さい）
ブラウザのネイティブ解凍速い速い
JavaScript での解凍まあ速い明確に遅い
ビルド時間速い遅い
向いている場面Fallback ON のときFallback OFF のとき

これが前回 GitHub Pages に対して Gzip を推した理由です。ヘッダを設定できない環境では JavaScript で解凍するしかなく、そこでは Brotli の「小さい」という利点が「解凍が遅い」で相殺されてしまうからです。

結論はホスティングとセットで決まります。

ホスティング圧縮形式Fallback
Cloudflare Pages / Netlify / VercelBrotliOFF
GitHub PagesGzipON

補足：Unity の設定画面では Project Settings → Player → Publishing Settings にある Compression Format と Decompression Fallback がこれにあたります。切り替えは再ビルドが必要ですが、設定自体は 2 クリックです。

Decision D8

Unity と Web はどうやって会話するのか

D8SendMessage + .jslib + 単一の封筒

まず前提：Unity WebGL は「箱」である

Unity で書いた C# のコードは、WebGL ビルドすると WebAssembly という形式に変換されます。これはブラウザの中で動く、機械語に近い高速な形式です。

重要なのは、この WebAssembly の世界と、Web ページの JavaScript の世界が基本的に別世界だということです。C# から document.getElementById(...) を呼ぶことはできませんし、JavaScript から C# の変数を直接読むこともできません。

┌─────────────────────────────────────────┐
│  ブラウザのページ                        │
│                                         │
│  JavaScript の世界                       │
│  ・DOM（HTML の要素）                    │
│  ・React のコンポーネント                 │
│  ・URL、履歴                             │
│                                         │
│   ┌───────────────────────────────┐    │
│   │  Unity WebAssembly の世界      │    │
│   │  ・C# のクラス                  │    │
│   │  ・GameObject                  │    │
│   │  ・3D の描画                    │    │
│   │                               │    │
│   │  ← ここと外は直接つながっていない │
│   └───────────────────────────────┘    │
└─────────────────────────────────────────┘

そこで Unity は、この壁に2 つだけ穴を用意しています。

穴 その1：外から中へ ＝ SendMessage

// JavaScript 側
unityInstance.SendMessage("WebBridge", "Receive", "こんにちは");
//                         ↑GameObject名   ↑メソッド名   ↑引数（1個だけ）

シーンの中にある WebBridge という名前の GameObject を探し、そこに付いているスクリプトの Receive というメソッドを呼びます。渡せる引数は 1 個だけで、文字列か数値しか渡せません。この制約が後で効いてきます。

穴 その2：中から外へ ＝ .jslib プラグイン

.jslib は「C# から呼べる JavaScript 関数」を書いておくファイルです。Unity のビルドに一緒に埋め込まれます。

// Assets/Plugins/PortfolioBridge.jslib（JavaScript で書く）
mergeInto(LibraryManager.library, {
  PortfolioEmit: function (ptr) {
    var json = UTF8ToString(ptr);
    window.dispatchEvent(new CustomEvent("unity:message", { detail: json }));
  }
});

// C# 側からはこう呼ぶ
[DllImport("__Internal")] static extern void PortfolioEmit(string json);

他の選択肢を検討した結果

方式結果
postMessage不採用 これは「別のページ同士」が会話するための仕組みです。使うには Unity を <iframe> という入れ子のページに隔離する必要があり、そうすると画面サイズの調整・フォーカス・オーバーレイの重ね順が全部ややこしくなります。今回は Unity と Web が同じページにいるので、そもそも出番がありません。
Application.ExternalEval不採用 古い Unity の機能で、すでに非推奨・削除されています。
WebSocket / HTTP 通信不採用 サーバーが必要になります。今回は静的ファイルだけで完結する構成なので、サーバーを立てる理由がありません。
つまり D8 の「通信方式」の部分は、実は選択の余地がありません。Unity が公式に用意した穴は 2 つだけで、それを使う以外の道がない。前回の設計書で「比較」と書いたのは正確ではなく、実質は「他がなぜ使えないかの確認」でした。

本当に設計判断が必要なのは、その 2 つの穴をどう使うかです。ここから先が D8 の本体です。

本題：なぜ「封筒（envelope）」にするのか

さきほどの制約を思い出してください。SendMessage は引数を 1 個しか渡せない。では「言語を日本語にして」と「一時停止して」と「対話を次の行に進めて」を、どう伝え分けるか。

素朴なやり方 — メッセージの種類ごとにメソッドを作る

// Unity 側（C#）
public class WebBridge : MonoBehaviour {
  public void SetLanguage(string lang) { ... }
  public void SetPaused(string flag)   { ... }
  public void AdvanceDialogue(string index) { ... }
  // 新しい種類が増えるたび、ここにメソッドを足す
}

一見わかりやすいのですが、これには重大な問題があります。

新しいメッセージを 1 種類増やすたびに、Unity のコードを書き換えて WebGL を再ビルドしなければなりません。Unity の WebGL ビルドは、この規模のプロジェクトなら 1 回 20〜40 分かかります。「作品パネルを閉じたことを Unity に伝えたい」と思いつくたびに、40 分待つことになります。

さらに、複数の値を渡したくなった瞬間に破綻します。AdvanceDialogue に「対話 ID」と「行番号」の 2 つを渡したい。引数は 1 個しかない。すると結局 "cafe.intro:3" のような文字列を自作して、Unity 側で Split(':') することになります。自作フォーマットは必ず壊れます。

封筒方式 — 受け口を 1 つだけにする

// Unity 側（C#）— これ以降、増やさない
public class WebBridge : MonoBehaviour {
  public void Receive(string json) {
    var env = JsonUtility.FromJson<Envelope>(json);
    switch (env.type) {
      case "SET_LANGUAGE":      ...; break;
      case "SET_PAUSED":        ...; break;
      case "ADVANCE_DIALOGUE":  ...; break;
      default: Debug.LogWarning($"unknown: {env.type}"); break;
    }
  }
}
// 実際に送られてくる中身
{
  "v": 1,
  "id": "a3f9",
  "type": "ADVANCE_DIALOGUE",
  "payload": { "dialogueId": "cafe.intro", "lineIndex": 3 },
  "ts": 1755331200000
}

Receive という受け口はもう二度と変えません。増えるのは switch の分岐だけです。そして payload は JSON なので、いくつでも値を入れられます。

封筒の各項目がなぜ必要か

項目なぜ必要か
typeどの処理に振り分けるか。これがないと封筒の意味がない
payload実際のデータ。ここが自由な形なので、引数 1 個の制約を回避できる
v
バージョン		これが一番わかりにくいので詳しく説明します。Unity のビルドと Web の更新は別々に行われます。Web は数分でデプロイできるので頻繁に更新しますが、Unity は 40 分かかるのでたまにしか更新しません。

すると必ず「Web は新しいのに Unity が古い」という状態が生まれます。そのとき Web が新しい形式のメッセージを送ると、古い Unity は理解できません。v があれば、「理解できないから無視する」という穏当な失敗ができます。なければ、解釈をしくじって予期しない挙動やクラッシュになります。
idデバッグ時に「送ったメッセージと届いたメッセージ」を突き合わせるため。無くても動きますが、うまく動かないときの原因究明が段違いに楽になります
ts
タイムスタンプ		同上。ログを時系列で並べられます

「未知の type は無視する」がなぜ重要か

ポートフォリオにおける最悪の失敗は、訪問者に真っ白な画面を見せることです。採用担当者が開いた瞬間にエラーで止まったら、内容以前に終わります。

知らないメッセージが来たときに例外を投げると、Unity の実行が止まり、世界が固まります。だから知らないものは黙って無視して、世界は動かし続ける。開発中はコンソールに警告が出るので気づけます。これは「エラー処理」というより「壊れ方を選ぶ」設計です。

BRIDGE_READY の握手がなぜ必要か

Unity のロードには数十秒かかります。その間、Web 側はもう動いています。訪問者が「日本語」を選ぶのは、Unity のロードが終わるずっと前かもしれません。

0 秒   Web が起動、Unity のロード開始
2 秒   訪問者が「日本語」をクリック
       → Web が SET_LANGUAGE を送る
       → まだ WebBridge という GameObject が存在しない
       → メッセージは何事もなく消える（エラーも出ない）
35 秒  Unity のロード完了
       → 言語が英語のまま。原因も分からない

これを防ぐために、Unity 側の準備ができたら「準備できました」と自分から言うようにします（BRIDGE_READY）。Web はそれを受け取るまで、送りたいメッセージをキューに貯めておく。届いた瞬間にまとめて流す。

0 秒   Web 起動、Unity ロード開始
2 秒   「日本語」クリック → キューに保存
35 秒  Unity → BRIDGE_READY
       Web → キューを一気に送信
       → 正しく日本語になる
この「握手してから話す」という形は、通信を扱うプログラムでは定番の型です。相手がいつ準備できるか分からないときは、準備完了の合図を待つ。ここを省くと、再現しづらいバグ（たまに言語が切り替わらない、等）に必ず悩まされます。

Decision D9

作品情報や文章をどこに置くか

D9コンテンツは TypeScript ファイル。zod は使わない

まず前回の提案を訂正します。「TypeScript + zod」と書きましたが、コンテンツ管理に zod は不要です。zod が要るのは Unity から飛んでくるメッセージの検証だけで、そこと混ぜて説明したのは私の説明不足でした。切り分けます（理由は後述）。

抽象的に比べても分かりにくいので、「公開後に説明文の誤字を見つけた。直して反映する」という一番よくある作業で比べます。

CMS を採らない理由

作業は確かに楽です。ただし引き換えに、外部サービスへの依存を抱えます。そのサービスが落ちればサイトも壊れる、無料枠の条件が変われば移行が必要になる、アカウントとAPIキーの管理が増える。1 人が 20 件の作品を管理するのに、この装備は重すぎます。チームで週に何十件も記事を出すなら話は別です。

Markdown を主役にしない理由

長い文章には最適です。ただし technologies: [Unity, C#] のような構造のあるデータには弱く、書き間違えても誰も教えてくれません。将来、本文が長くなったら「メタ情報は TypeScript、本文だけ Markdown」というハイブリッドにできます。それは必要になってから決めれば十分です。

JSON と TypeScript の違い ← ここが本題

この 2 つは見た目がほとんど同じです。違いは「間違えたとき、いつ気づけるか」だけです。

JSON の場合
{
  "id": "unity-horror-game",
  "titel": { "ja": "ホラーゲーム" },
  "technologies": ["Unity", "C#"]
}

title を titel と打ち間違えています。エディタは何も言いません。ビルドも通ります。気づくのは、公開されたサイトを開いて作品名の欄に undefined と表示されているのを見たときです。最悪の場合、それを見つけるのは採用担当者です。

TypeScript の場合
export const p: Project = {
  id: "unity-horror-game",
  titel: { ja: "ホラーゲーム" },
  technologies: ["Unity", "C#"]
}
// ↑ この時点でエディタに赤い波線
// 「'titel' は Project 型に存在しません」

打った瞬間に赤線が出て、ビルドも止まります。さらに ja: まで打った時点で、次に何を書けばいいかの候補が自動で出ます（補完）。間違えようがなくなります。

「型」というのは、Project というデータはこういう形をしているはずだ、という約束を先に書いておくことです。約束から外れたものを書いたら、その場で止めてくれます。

// この「約束」を 1 回だけ書いておく
type Project = {
  id: string;
  title: { ja: string; en: string };   // ja と en が両方必須
  technologies: string[];
  github?: string;                      // ? は「あってもなくてもいい」
}

この約束のおかげで、「英語版を書き忘れた作品」もビルド時に見つかります。20 件を手作業でチェックする必要がなくなる、というのが実務上いちばん効く利点です。

「Git が CMS になる」の意味

コンテンツをリポジトリのファイルとして持つと、副産物としてこうなります。

  • いつ・どの文章を・どう変えたかが全部残る（git log）
  • 「英語版を全部書き直す」ような作業をブランチで進めて、納得してから反映できる
  • 間違えて消しても取り戻せる
  • Claude Code に「この作品の説明をもっと簡潔にして」と頼める（ファイルなので直接編集できる）

では zod はどこで使うのか

ここが前回の説明で混ざっていた部分です。TypeScript の型は、ビルドが終わった瞬間に消えます。

開発中           型がある  → 間違いを検出できる
    ↓ ビルド
実行中（ブラウザ） 型は存在しない → 何も検査されない

自分で書いたコンテンツはビルドの時点で検査が終わっているので、実行時にもう一度調べる必要がありません。だからコンテンツに zod は不要です。

一方、Unity から実行時に飛んでくるメッセージは話が違います。それはビルド時には存在しないデータで、しかも「古い Unity ビルド」から来るかもしれません。ここは実行時に形を確かめる必要があり、そのための道具が zod です。

データいつ存在するか検査
作品情報・セリフ・UI 文字列ビルド時に確定TypeScript の型だけ（zod 不要）
Unity から届くメッセージ実行時に外から来るzod で実行時に検証

D9 の修正案：「コンテンツは TypeScript のみ。zod はブリッジの受信部分だけで使う」。覚えることが 1 つ減り、書くコードも減ります。
