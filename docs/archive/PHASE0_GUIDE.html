Phase 0 · 実行手順

現状の CAFE を Web で動かして、
実機で計測する

ここでやることは「作る」ではなく「測る」です。新しいコードは 1 行も書きません。今ある CafeScene をそのまま Web ビルドし、iPhone で開いて、数字を 4 つ記録します。その数字がホスティング（D3）を自動的に決めます。

Good news

Phase 0 では Web アプリを作る必要すらありません

Unity の WebGL ビルド出力には、最初から index.html が含まれています。つまり、ビルドしたフォルダをそのまま静的サーバーに置けば、それだけでブラウザで動きます。

Next.js もリポジトリも Phase 0 では不要です。それらは Phase 1 から。さらに言えば、最初の計測はデプロイすらせず、Mac のローカルサーバーと同じ Wi-Fi の iPhone だけで完結します。ホスティングを決めずに進める、という判断とも噛み合います。

Phase 0 の全体像
Unity でビルド → Mac でサイズを測る → Mac にローカルサーバーを立てる → 同じ Wi-Fi の iPhone で開く → 数字を記録する
所要：Unity のビルド待ち時間を除けば、実作業は 30 分程度です。

Before you start

先に知っておくべき 3 つのこと

1. プラットフォーム切替に非常に時間がかかります

Unity のプラットフォームを Web に切り替えると、887 MB のアセットが全部再インポートされます。テクスチャの圧縮形式が変わるためです。この処理は環境によりますが 30 分〜2 時間以上かかることがあります。夜に始めて放置するのが現実的です。

再インポートの成果物は Library/ に入りますが、ここは .gitignore で除外済みなので Git には一切影響しません。安心して切り替えてください。ただしディスク容量は数 GB 増えます（現在すでに 6.2 GB）。空き容量を確認しておいてください。

2. 初回ビルドは失敗する前提でいてください

Unity の Web ビルドは、初回に何らかのエラーで止まることがよくあります。よくある原因は Web で使えない API の参照、パッケージの非対応、IL2CPP のコンパイルエラーなどです。これは異常ではなく通常です。エラーが出たら、そのログをそのまま貼っていただければ一緒に潰します。

また、初回はコードのコンパイル（IL2CPP）に 30〜90 分かかります。2 回目以降はキャッシュが効いて速くなります。

3. 今回の設定は「最終形」ではありません

これから指定する圧縮設定は、どのホスティングでも動く中立的な設定です。ホスティングを決めた後にもう一度ビルドし直して最適化します。Phase 0 の目的は最速の設定を出すことではなく、数字を得ることです。

Step 1

Unity でビルドする

1プラットフォームを Web に切り替える

File → Build Profiles

Unity 6 では従来の Build Settings が Build Profiles に変わっています。File → Build Profiles を開き、左のリストから Web を選んで Switch Platform を押してください。

ここで前述の長い再インポートが始まります。完了するまで Unity を触らずに待ってください。

2ビルドに含めるシーンを CafeScene だけにする

Build Profiles → Scene List

同じ Build Profiles の画面に Scene List があります。ここを Assets/Scenes/CafeScene.unity の 1 つだけにしてください。

これが最も重要な設定です。Scene List に含まれるシーンが参照しているアセットが、すべてビルドに焼き込まれます。VillageScene や SampleScene が混ざっていると、CAFE では使わない大量のアセットまでダウンロード対象になり、測る意味がなくなります。

3Player Settings を設定する

Build Profiles → Player Settings（または Edit → Project Settings → Player）

Publishing Settings（Web タブの中）

Compression FormatBrotli
Decompression FallbackON（チェックを入れる）
Data CachingON（既定のまま）
Name Files As HashesOFF

なぜこの組み合わせか：Brotli にするのは、生成される .data の Brotli 圧縮後サイズが分かれば、そのまま「Cloudflare Pages の 25 MiB 制限に収まるか」の判定に使えるからです。Fallback を ON にするのは、これがあればヘッダを設定できない環境（ローカルの簡易サーバーや GitHub Pages）でも動くからです。この設定なら、どこに置いても必ず動きます。その代わり起動は最も遅い条件になるので、計測値は「最悪ケース」だと考えてください。

Name Files As Hashes を OFF にする理由：ON だとファイル名がランダムな文字列になり、どれが .data なのか読み取れなくなります。サイズを測るのが目的なので OFF にします。

Other Settings

Scripting BackendIL2CPP（Web では固定）
Managed Stripping Level既定のまま触らない
Enable Exceptions既定のまま触らない

前回の設計書では Managed Stripping を High にすると書きましたが、Phase 0 では触らないでください。High にするとコードは小さくなりますが、Visual Scripting のようにリフレクションを使うパッケージが動かなくなることがあります。Phase 0 の目的は「まず動くこと」なので、最適化は後回しにします。この設定を触るのは Phase 1 以降です。

Build Profiles 画面の下部

Development BuildOFF（チェックを外す）

Development Build が ON だとデバッグ情報が大量に埋め込まれ、サイズが数十 MB 単位で膨らみます。計測の邪魔になるので必ず外してください。

4ビルドする

Build Profiles → Build

出力先は ~/Unity/MyWorld/Build/WebGL/ にしてください。Build/ は .gitignore で除外済みなので、Git に混ざる心配はありません。

ここで 30〜90 分かかります。エラーで止まったらログを貼ってください。

Step 2

サイズを測る

ビルドが終わったら、Mac のターミナルで次を実行してください。

cd ~/Unity/MyWorld/Build/WebGL
# 全体のサイズ
du -sh .
# ファイルごとのサイズ（大きい順）
ls -lhS Build/

Build/ の中に、こういうファイルができているはずです。Decompression Fallback が ON なので拡張子は .unityweb になります。

ファイル中身注目度
WebGL.data.unityweb3D モデル・テクスチャ・音・シーン最重要 ここが全体の大半
WebGL.wasm.unitywebゲームのコード（Unity エンジン込み）だいたい 5〜10 MB
WebGL.framework.js.unitywebエンジンと JS をつなぐ層小さい
WebGL.loader.js読み込みを担当（唯一圧縮されない）小さい
記録するのはこの 2 つ
① .data.unityweb のサイズ→ D3（ホスティング）を決める
② Build/ フォルダ全体のサイズ→ 訪問者のダウンロード総量

Step 3

iPhone の実機で開く

Mac に簡易サーバーを立てて、同じ Wi-Fi につないだ iPhone からアクセスします。Mac に最初から入っている Python を使うので、何もインストールする必要はありません。

# ターミナル 1：サーバーを起動（ビルドフォルダの中で実行）
cd ~/Unity/MyWorld/Build/WebGL
python3 -m http.server 8000
# ターミナル 2：Mac の LAN 内 IP アドレスを調べる
ipconfig getifaddr en0
# 例: 192.168.1.23  ← 何も出なければ en1 も試す

iPhone の Safari で http://192.168.1.23:8000（上で出た IP）を開いてください。Mac と iPhone が同じ Wi-Fi につながっている必要があります。

ここでもし動かなくても、まだ諦めないでください。Mac のファイアウォールがブロックしている可能性があります（システム設定 → ネットワーク → ファイアウォール）。それでも駄目なら、この Step は飛ばして Mac の Chrome / Safari だけで計測し、実機確認は公開デプロイ後に回しても構いません。

計測のしかた

  • ロード時間 — URL を開いてから 3D の画面が出るまでをストップウォッチで。2 回測ってください（1 回目 = 初回訪問者の体験、2 回目 = キャッシュが効いた状態）
  • クラッシュの有無 — 途中でページが白くなったり勝手に再読み込みされたら、メモリ不足です。これが起きたかどうかを必ず記録してください
  • フレームレート — 正確な数値は不要です。「歩いたときにカクつくか」を体感で。滑らか / 少しカクつく / 明らかに重い、の 3 段階で十分です
  • 操作できるか — スマホにはキーボードがないので、おそらくまったく動かせません。これは正常です（モバイル入力は Phase 1 で作ります）。画面が出て、カクついていないかだけ見てください

Interpretation

結果をどう読むか — ここで D3 が自動的に決まります

① .data.unityweb のサイズ → ホスティングが決まる

サイズ意味次の一手
25 MiB 未満理想的Cloudflare Pages が使える（帯域無制限・最速）
25〜60 MB許容範囲Netlify。または Cloudflare を使うためにアセット削減
60〜100 MB要対策先にテクスチャ解像度を下げる。Phase 1 に進む前に
100 MB 超設計以前の問題使用アセットの選定から見直し

③ ロード時間 → 体験が成立するか

今回は「最も遅い条件」での計測なので、実際の公開時にはここから 20〜40% 改善します（ヘッダを設定できるホストに置けば、転送量が減り、解凍がブラウザのネイティブ処理になるため）。

計測値判定
30 秒未満問題なし このまま Phase 1 へ
30〜60 秒要工夫 ホスティング最適化 + ローディング画面の作り込みで許容範囲に
60 秒超対策必須 Phase 1 の前にアセット削減

④ クラッシュ → 最も深刻な問題

iPhone でクラッシュする場合、訪問者からは「壊れたサイト」にしか見えません。サイズ以上に優先して対処すべき問題です。この場合は Player Settings のメモリ設定とテクスチャ解像度を一緒に詰めます。

After

Phase 0 の後にやること

  1. 結果を共有していただく — 記録シートの 6 項目
  2. D3 を確定する — ①の数字で自動的に決まります
  3. 公開デプロイ — 決まったホスティングに置いて、公開 URL でもう一度確認（ここは私が手順を用意します）
  4. 設計書を更新 — 計測値を ARCHITECTURE.md に追記して、Phase 1 の前提を確定させる
  5. Phase 1 着手 — EVENT_SCHEMA.md の確定 → Unity Bridge → Web Bridge の順
私の側で先に進めておけること

Unity のビルド待ちの間、ご希望があれば次を並行して用意できます。どちらも Phase 0 の結果に依存しません。

  • docs/EVENT_SCHEMA.md — Unity と Web が交換するメッセージの契約書（Phase 1 の最初の作業）
  • Web リポジトリの雛形 — Next.js の初期構成一式

つまずいたら、エラーログでも画面のスクリーンショットでも、そのまま貼ってください。Unity の設定画面は バージョンによって項目の位置が変わることがあるので、見つからない項目があればその旨を伝えていただければ探します。
